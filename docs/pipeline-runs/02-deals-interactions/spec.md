# Spec: Deals and Interactions modules

## Task

Add `Deal` and `Interaction` Prisma models (one migration, `add_deals_and_interactions`, generated with `prisma migrate dev`) and two API modules, `deals` and `interactions`. They follow the companies/contacts pattern: same layering, pagination, validation, error shape and tests. `DealService` owns the `closedAt` business rule. Extend the seed with 8 deals and 2 to 5 interactions each. Do not add the embedding column, AI features or scoring.

## Requirements

### Data model
1. `Deal` has these fields:
   - `id`: UUID, generated by Prisma (`@default(uuid()) @db.Uuid`).
   - `companyId`: UUID, required, FK to `Company.id`, `ON DELETE CASCADE`.
   - `title`: text, required.
   - `value`: `DECIMAL(12,2)`, required.
   - `stage`: Postgres enum `DealStage` (`LEAD`, `QUALIFIED`, `PROPOSAL`, `NEGOTIATION`, `WON`, `LOST`), required, default `LEAD`.
   - `expectedCloseDate`: `DATE`, nullable.
   - `closedAt`: `TIMESTAMP(3)`, nullable.
   - `createdAt`: default now. `updatedAt`: `@updatedAt`.
2. `Interaction` has these fields:
   - `id`: UUID, generated by Prisma.
   - `dealId`: UUID, required, FK to `Deal.id`, `ON DELETE CASCADE`.
   - `type`: Postgres enum `InteractionType` (`EMAIL`, `CALL`, `MEETING`, `NOTE`), required.
   - `notes`: text, required.
   - `occurredAt`: `TIMESTAMP(3)`, required, default `CURRENT_TIMESTAMP`.
   - `createdAt`: default now. `updatedAt`: `@updatedAt`.
   - There is no `embedding` column.
3. Deleting a company deletes its deals, and through them their interactions. Deleting a deal deletes its interactions. Both are done by DB foreign keys.
4. There is exactly one new migration folder, ending in `_add_deals_and_interactions`, generated by `npm --prefix api run migrate -- --name add_deals_and_interactions`. It sorts after `20261028120000_add_companies_and_contacts`.

### Resource shapes (JSON)
5. Deal: `{ id, companyId, title, value, stage, expectedCloseDate, closedAt, createdAt, updatedAt }`.
   - `value` is a JSON number. For example, 48500.5 is returned as `48500.5`, not as `"48500.50"`.
   - `expectedCloseDate` is a `"YYYY-MM-DD"` string or `null`.
   - `closedAt`, `createdAt` and `updatedAt` are ISO 8601 strings. `closedAt` can also be `null`.
   - The response does not embed interactions or the company.
6. Interaction: `{ id, dealId, type, notes, occurredAt, createdAt, updatedAt }`. All dates are ISO 8601 strings. The response does not embed the deal.

### Endpoints
7. `GET /companies/:companyId/deals` returns 200 with `{ data: Deal[], meta }`, containing only that company's deals.
8. `POST /companies/:companyId/deals` returns 201 with the created Deal. `companyId` comes from the URL.
9. `GET /deals` returns 200 with `{ data: Deal[], meta }` across all companies. It supports the optional filters `?stage=<DealStage>` and `?companyId=<uuid>`. When both are given they are combined with AND. `meta.total` counts only the filtered rows.
10. `GET /deals/:id` returns 200. `PATCH /deals/:id` does a partial update and returns 200. `DELETE /deals/:id` returns 204 with an empty body.
11. `GET /deals/:dealId/interactions` returns 200 with `{ data: Interaction[], meta }`, containing only that deal's interactions.
12. `POST /deals/:dealId/interactions` returns 201 with the created Interaction. `dealId` comes from the URL.
13. `GET /interactions/:id` returns 200. `PATCH /interactions/:id` does a partial update and returns 200. `DELETE /interactions/:id` returns 204 with an empty body.

### Validation (all failures: 400 `{ error: { code: "VALIDATION_ERROR", message, details } }`)
14. Bodies are strict objects, so unknown keys return 400. This rejects:
    - `id`, `createdAt` and `updatedAt` on any body.
    - `companyId` and `closedAt` on deal bodies.
    - `dealId` on interaction bodies.
15. `title` is trimmed, then must be 1 to 200 characters. It is required on POST and optional on PATCH. It is never nullable.
16. `value`:
    - It must be a JSON number (a string such as `"100"` returns 400).
    - It must be between 0 and 9999999999.99 inclusive, with at most 2 decimal places (`12.345`, `0.1 + 0.2` and `1e-7` return 400).
    - It is required on POST, optional on PATCH, and never nullable.
17. `stage` must be one of the six values, case-sensitive (`"won"` returns 400).
    - It is optional on POST, where it defaults to `LEAD`.
    - It is optional on PATCH and never nullable.
18. `expectedCloseDate`:
    - It must be a real calendar date in `YYYY-MM-DD` format. `2026-02-30`, `2026-13-01`, `2026-1-5` and `2026-01-01T00:00:00Z` all return 400.
    - The year must be between 1900 and 9999.
    - Past dates are allowed.
    - It is optional and nullable on POST and on PATCH. `null` on PATCH clears it.
19. `type` must be one of `EMAIL`, `CALL`, `MEETING`, `NOTE`, case-sensitive. It is required on POST, optional on PATCH, and never nullable.
20. `notes` is trimmed, then must be 1 to 5000 characters. It is required on POST, optional on PATCH, and never nullable.
21. `occurredAt`:
    - It must be an ISO 8601 datetime with a `Z` or a numeric offset (`z.iso.datetime({ offset: true })`). A date-only value or a local time without an offset returns 400.
    - A value later than the server's current time returns 400.
    - A value before `1900-01-01T00:00:00Z` returns 400.
    - It is optional on POST, where it defaults to the time of insertion (DB default). It is optional on PATCH and never nullable.
22. A PATCH body with no keys (`{}`) returns 400. So does a missing body or a body that is not an object.
23. Route params `:id`, `:companyId` and `:dealId` must be UUIDs (`z.uuid()`). Otherwise the response is 400.
24. Pagination (`page`, `pageSize`) follows the existing `paginationQuerySchema` rules on all four list endpoints.
25. On `GET /deals`:
    - `stage` must be a valid stage, and `companyId` must be a UUID.
    - An empty value (`?stage=`) returns 400, and so does a repeated key (`?stage=WON&stage=LOST`).
    - Unknown query keys are ignored.
26. Validation order in each handler is params, then query, then body.

### Not found (404 `{ error: { code: "NOT_FOUND", message } }`)
27. `GET` and `POST /companies/:companyId/deals` return 404 with `Company <companyId> not found` when the company does not exist. No deal is created.
28. `GET`, `PATCH` and `DELETE /deals/:id` return 404 with `Deal <id> not found`.
29. `GET` and `POST /deals/:dealId/interactions` return 404 with `Deal <dealId> not found` when the deal does not exist. No interaction is created.
30. `GET`, `PATCH` and `DELETE /interactions/:id` return 404 with `Interaction <id> not found`.
31. `GET /deals?companyId=<valid uuid of a missing company>` is a filter, not a parent lookup. It returns 200 with an empty list.

### Business rule: closedAt (DealService)
32. `closedAt` is never accepted from the client (rule 14).
33. On create:
    - If the resulting stage is `WON` or `LOST`, `closedAt` is set to the current time.
    - Otherwise (including the default `LEAD`), `closedAt` is `null`.
34. On PATCH with `stage`, the service reads the current deal and applies these rules:
    - Open to `WON`/`LOST`: set `closedAt` to now.
    - `WON`/`LOST` to an open stage: set `closedAt` to `null`.
    - `WON` to `LOST` or `LOST` to `WON`: set `closedAt` to now. The stage changed to a closed stage.
    - Same stage as now (for example `WON` to `WON`): `closedAt` is unchanged.
    - Open to a different open stage: `closedAt` is unchanged.
35. On PATCH without `stage`, `closedAt` is unchanged, and the service does not read the current deal.

### Lists
36. Deal lists (both endpoints) are ordered by `createdAt desc, id desc`. Interaction lists are ordered by `occurredAt desc, id desc`.
37. Pagination uses `toSkipTake`/`toPaginated`. A page past the end returns 200 with `data: []` and the correct `total`.

### Seed
38. `npm --prefix api run seed` stays idempotent.
    - It keeps the existing 5 companies and 12 contacts unchanged.
    - It adds 8 deals spread over the companies, covering all six stages, with 2 to 5 interactions each. Concrete data is in the plan below.
    - Running it twice leaves exactly 5 companies, 12 contacts, 8 deals and 26 interactions.

## Edge cases

- **Decimal serialization.** Prisma returns `value` as a `Prisma.Decimal`, which `JSON.stringify` turns into a string. The repository must convert it with `.toNumber()`. `DECIMAL(12,2)` values (max 9999999999.99, that is 10^12 cents) round-trip exactly through doubles and JSON.
- **Decimal places on floats.** Check them on `String(value)`, matching `/^\d+(\.\d{1,2})?$/`, after the `min(0)` and `max` checks. This rejects `0.30000000000000004` and exponent forms such as `1e-7`, and accepts `5`, `5.1` and `5.10` (which JSON parses as `5.1`). `-0` passes `min(0)` and `String(-0)` is `"0"`, so it is stored as 0. That is acceptable.
- **Value overflow.** Without the `max`, a value of 1e10 or more would make Postgres throw (numeric field overflow), giving a 500. The `max(9_999_999_999.99)` prevents that.
- **NaN/Infinity** cannot come from JSON, and zod v4 `z.number()` rejects them anyway.
- **Date-only timezone shift.**
  - Write `expectedCloseDate` as `new Date(\`${s}T00:00:00.000Z\`)`.
  - Read it with `date.toISOString().slice(0, 10)`, using UTC. Never use local getters such as `getDate()`.
  - The machine running the tests may not be in UTC. AC 3's round trip catches a shift.
- **Invalid calendar dates.** zod v4 `z.iso.date()` checks days per month and leap years. Cover `2026-02-30`, `2025-02-29` (rejected) and `2024-02-29` (accepted) with unit tests.
- **Extreme years.** Year `0000` and very old timestamps may not round-trip through `pg`. The 1900 lower bound on `expectedCloseDate` and `occurredAt` avoids 500s. `z.iso.date()` limits years to 4 digits, so the upper bound is 9999.
- **The future check uses the time of parsing.**
  - An `occurredAt` equal to "now" is accepted (`<=`).
  - Client clock skew of even 1 ms into the future returns 400. That is accepted strictness.
  - Tests use a value at least one hour in the future.
- **Offsets.** `+02:00` is normalized to UTC on storage. A datetime with more than 3 fractional digits is accepted and truncated to milliseconds by `TIMESTAMP(3)`.
- **Notes length** is counted in UTF-16 code units after trimming, which is zod's default.
- **PATCH stage on a vanished deal.** `findById` returns null, which gives a 404, and `update` is not called. If the deal disappears between `findById` and `update`, the repository returns null on P2025, which also gives a 404.
- **Concurrent stage PATCHes.** Two simultaneous stage changes could each compute `closedAt` from a stale read. The app is single-user, so this is accepted and not locked (see the assumptions).
- **Same-stage PATCH** (`WON` to `WON`) is not a change, so `closedAt` is kept. The repository data must not contain a `closedAt` key at all, not even `undefined`. Unit tests check this with `not.toHaveProperty("closedAt")`.
- **Inconsistent legacy rows.** A `WON` deal with `closedAt: null` (seed or manual SQL) is left as it is by a same-stage PATCH. A PATCH to `LOST` sets it to now.
- **Filter vs parent.** `/deals?companyId=<missing>` returns 200 with an empty list. `/companies/<missing>/deals` returns 404.
- **Repeated query keys** produce an array, which fails `z.enum`/`z.uuid` with 400.
- **Nested deal list and `?stage`.** `GET /companies/:companyId/deals?stage=WON` ignores `stage`, because unknown keys are ignored (see the assumptions).
- **Deleting a company with deals.** It cascades through two levels. Postgres handles this with the FK chain, and no application code is needed.
- **Interactions on closed deals** are allowed. No stage check is made.
- **Equal `occurredAt`.** The `id desc` tiebreak keeps the order stable.
- **Nil UUID** on new routes gives 404, not 500.
- **Integration isolation.** `resetDatabase` truncates the new tables automatically, because it reads `pg_tables`.

### Prisma schema (add to `api/prisma/schema.prisma`)

```prisma
enum DealStage {
  LEAD
  QUALIFIED
  PROPOSAL
  NEGOTIATION
  WON
```

### Data flow

- **Request path.** HTTP, then router, then controller (`parseOrThrow` params, then query, then body), then service, then repository interface, then Prisma.
- **Deal create.**
  1. Zod gives `CreateDealInput`, with `stage` defaulted and `expectedCloseDate` as a string.
  2. The service adds `closedAt`, giving `CreateDealData`.
  3. The repository converts the date string to a UTC-midnight `Date` and inserts the row.
  4. The repository maps the row with `toDeal` (Decimal to number, Date to `YYYY-MM-DD`).
  5. The controller sends 201 JSON. Express serializes `closedAt`, `createdAt` and `updatedAt` as ISO strings.
- **Deal PATCH with stage.**
  1. Zod gives `UpdateDealInput`.
  2. The service calls `findById` to get the current `Deal`.
  3. `withClosedAtForStageChange` gives `UpdateDealData`.
  4. The repository runs `update`.
  5. The deal is mapped and returned with 200.
- **`GET /deals`.** Zod parses `ListDealsQuery`. The controller splits it into `DealListFilter` and `Pagination`. The service calls `repository.list`, and `toPaginated` builds the response.
- **Interaction create.** Zod gives `CreateInteractionInput`, with `occurredAt` as a `Date` or undefined. The service checks that the deal exists, then the repository inserts the row. The DB default fills in `occurredAt` when it was omitted.

### Conventions to follow

- Layers go one way only: routes -> controller -> service -> repository -> Prisma.
  - Services import only repository interfaces and domain types from `*.schemas.ts`, never `generated/prisma`.
  - Only repositories import `generated/prisma` and `shared/prisma-errors.ts`.
- Use constructor injection. All instantiation happens in `container.ts`. A module may depend on another module's repository interface (as contacts depends on `CompanyRepository`), but not on its schemas. That is why `companyIdParamsSchema` moves to shared.
- ESM imports end in `.js`. Use `import type` for type-only imports (`verbatimModuleSyntax`). No `any`. Keep strict mode and `noUncheckedIndexedAccess` in mind.
- Controller handlers are arrow-function class properties. Follow the `<module>.<layer>.ts` naming. Router factories are named `create<Thing>Router`.
- Throw `NotFoundError`/`ValidationError` from `shared/errors.ts`. Do not change `error-middleware.ts`.
- Use the existing message constants (`INVALID_PARAMS_MESSAGE`, and so on).
- Test names describe behavior.
- Do not add an `embedding` column, AI code or scoring code. Do not touch `.claude/`. Run no git commands that change history.
- Explain the non-obvious decisions in `.pipeline/implementation.md`: the Decimal mapping, the date-only handling, why the `closedAt` rule reads the current deal, and why the move of `companyIdParamsSchema` was made.

## Open questions / assumptions

1. **WON ↔ LOST.** I read "changes to WON or LOST" literally: switching between the two closed stages resets `closedAt` to now. A same-stage PATCH is not a change and keeps `closedAt`.
2. **Creating directly as WON/LOST** sets `closedAt` to now. This is consistent with the rule: the deal "became" closed at creation.
3. **`value` is required on create** and never nullable. The task gives no default, and a missing amount would make later scoring ambiguous.
4. **Upper bound for `value`** is 9999999999.99, implied by `DECIMAL(12,2)`. It is enforced as a 400 so the DB never overflows into a 500.
5. **Lower bound of 1900 on dates and no upper bound** on `expectedCloseDate` apart from year 9999. Past expected close dates are allowed, because the seed needs them and real data has them.
6. **The `occurredAt` future check has zero tolerance** for clock skew, exactly as stated. An equal-to-now value is accepted.
7. **`occurredAt` requires a timezone** (`Z` or an offset). Local times without one are ambiguous and are rejected.
8. **No clock abstraction.** "Now" is `new Date()`/`Date.now()`, and tests use Vitest fake timers. This avoids a new abstraction for a single call site. It can become an injected `Clock` later if scoring needs one.
9. **Concurrency of the stage PATCH.** The read-then-write is not wrapped in a transaction or lock. The app is single-user and the worst case is a slightly stale `closedAt`. The deleted-in-between case still returns 404 through the P2025 mapping.
10. **The nested `GET /companies/:companyId/deals` supports pagination only.** A `?stage` there is ignored, like any unknown key. Filtering is on `GET /deals` as the task specifies.
11. **`GET /deals?companyId=` for a missing company** returns 200 with an empty list, because it is a filter, not a parent route.
12. **The domain `Deal` uses `value: number` and `expectedCloseDate: string`** (the API shape). The repository does the conversion, so no Prisma type leaks into services.
