# Review: semantic search over interaction notes (POST /ask, retrieval only)

## Summary
The change is correct, complete and follows the spec closely, and it is consistent with CLAUDE.md. The migration is ordered correctly. All vector SQL sits in two repositories and uses parameterized tagged templates. The similarity threshold is NaN-safe. The embedding lifecycle (save, then embed, then a compare-and-set write, with a clear on failure) is race-safe. `LocalEmbeddingProvider` caches the load promise and resets it on failure. Tests cannot reach the real model. Lint, typecheck and all 825 tests pass, and every acceptance criterion is covered. I found no Critical or High issues. The main open point is a migration workflow gap: CLAUDE.md now says how to *create* a migration without dropping the HNSW index, but not how to *apply* one, and `prisma migrate dev` will notice the drift again when applying. The other findings are small: test and documentation polish, plus manual checks that the pipeline could not run (seed, real model).

### Medium
- **CLAUDE.md:52 (the new note below the Commands table) and CLAUDE.md:47 (`New migration` row): the apply step for future migrations is missing.** The note says to create migrations with `--create-only` and strip `DROP INDEX "Interaction_embedding_hnsw_idx"`. But applying a migration with `npm --prefix api run migrate` (`prisma migrate dev`) diffs `schema.prisma` against the database again after applying. It will find the hand-made index again and prompt for, or try to generate, a migration that drops it. The `migrate dev` "hang after applying" in implementation.md ("Migration and Prisma drift check", operational note) is very likely that interactive prompt and not a lock problem. A future agent or the human following the table can therefore still lose the index, or get stuck.
  **Fix:** in the same note, say that the edited migration is applied with `npm --prefix api exec -- prisma migrate deploy`, not `migrate dev`. Optionally add an `api/package.json` script such as `"migrate:deploy": "prisma migrate deploy"` and a table row for it. Also put `--create-only` into the `New migration` row so the row and the note no longer disagree. Correct the operational note in implementation.md to match.

### Low

The extra tie-breaker `, i."id" ASC` and the JOINs mean the planner may never use the index, and pgvector documents index use for `ORDER BY embedding <=> $1 LIMIT n`. That is harmless at this scale and it makes results exact (see the documented ef_search limitation), but the comment should not promise index use. **Fix:** check with `EXPLAIN` on a seeded database and either reword the comment ("deterministic tie-break; the planner may prefer an exact scan at this scale") or add the finding to implementation.md.

If the note only describes the JSON response, it is misleading. **Fix:** check `row.occurredAt instanceof Date` once against the test DB. ## Checks against the orchestrator's focus list
- **Migration:** `20261029124549_add_interaction_embeddings` sorts after `20261028000000_enable_pgvector`, so the `vector` type exists, in the shadow database too. The column is nullable `vector(384)` and the index is `USING hnsw ("embedding" vector_cosine_ops)`. `schema.prisma` declares `embedding Unsupported("vector(384)")?` with the required comment. OK.
- **SQL safety:** `<=>` and `::vector` occur only in `ask.repository.ts` and `interactions.repository.ts` (plus a comment in `shared/pgvector.ts`). There is no `*Unsafe` in `src`. The vector is one bound text parameter built by `toVectorLiteral`, which rejects non-finite values. `embedding` is never selected raw. OK.
- **Similarity:** `1 - (embedding <=> q)` is correct. The threshold `MIN_SIMILARITY = 0.25` is a named constant and is applied as `distance <= 0.75`, which excludes NaN and negative cosines (distance > 1). The order is distance ascending, which is similarity descending, with an id tie-break. `IS NOT NULL` skips rows without an embedding, the `dealId` filter is null-safe, and `LIMIT` is bound. The clamp and rounding are in the service. OK.
- **404 and validation:** the deal check runs before embedding. `z.strictObject` handles trimming, 3 to 500 chars, int 1 to 10 with default 5, `dealId: null` rejected and arrays rejected. All are covered by the table-driven integration test. OK.
- **Response shape:** the excerpt is cut on code points (300), similarity has 3 decimals and is clamped, `answer: null` and `answeredBy: "none"`. OK.
- **Embedding on create and PATCH:** embeds after a successful create, and only when `notes` is in the PATCH. `refreshEmbedding` never rejects. Warnings carry only ids and `describeError`. The compare-and-set `WHERE notes = $notes` on save and on clear prevents stale vectors from concurrent PATCHes or a PATCH during the backfill. The one remaining interleaving (A-B-A notes with a late failure-clear) can only produce NULL, never a wrong vector, and the backfill repairs it. OK.
- **LocalEmbeddingProvider:** the promise is cached with `??=`, which runs synchronously before the first await, so concurrent callers share one load. It resets on rejection, passes `{ pooling: "mean", normalize: true }`, and validates dims, row count and data length. OK.
- **Backfill:** a keyset loop with a batch size of 32. Every batch advances `afterId`, so the loop terminates even when every batch fails. It counts updated and failed, and lets database errors propagate. `run-embedding-backfill.ts`, `embed-backfill.ts` and the seed hook only wire, print, set the exit code and disconnect. OK.
- **container.ts:** the provider is chosen only in `createEmbeddingProvider()` and typed as the interface. The dimension check runs before `PrismaClient` is built. The library is imported dynamically, so importing the container loads nothing. Every integration file uses `createTestContainer`, which injects the fake. OK.
- **Planner additions:** the 503 `EMBEDDING_UNAVAILABLE` error is a sensible mapping for a retryable dependency failure and is documented. Clearing the vector on a failed re-embed carries the task's "null embedding on failure" rule over to PATCH and prevents misleading results. The dimension check is cheap fail-fast. All three fit the task.
- **General:** the layers are respected, the new classes use constructor injection, there is no `any` in `src`, no CR characters, and named constants are used throughout.
- **Tests:** `it.each` is used where cases differ only by data. The fake's vectors give 0.316 and 0.243 for question "price", which sit on both sides of 0.25 and away from float4 noise. The checks for "loads once", "retries after failure" and "no provider call on 404 or validation errors" can each fail. The only duplication is noted above.
- **implementation.md:** it justifies the dependency (version, why it is needed, size, onnxruntime and sharp), documents the HNSW-with-filters limitation and records the drift finding. OK, apart from the operational note (Medium finding).
